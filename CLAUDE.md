# Woven — Claude Code Developer Guidance

**Purpose:** Open-source, local-first AI agent platform — a modular, model-agnostic runtime combining models, tools, context, memory, workflows, projects/workspaces, permissions, and multiple clients.

**Current state:** `src/woven/` implements `AgentRuntime` with `chat`/`plan`/`code` Modes, `Model`/`Tool`/`Context`/`ApprovalPolicy` protocols (with `FakeModel`/`MockTools`/`FilesystemContext`/`AutoApprovalPolicy` as the current implementations), and Events. See `docs/architecture/agent-runtime.md` (design) and `docs/architecture/decisions.md` (why). `src/woven/settings/` persists a local `User` identity and `Settings` (default mode/permission tier, model-provider placeholder) to `~/.config/woven/config.json`, plus a `SecretStore`-backed `~/.config/woven/secrets.json` for per-provider API keys (currently Gemini) — see `docs/architecture/user-settings.md`. The CLI client (`woven chat`, `src/woven/client/cli/`) is at parity with all of it — three selectable permission tiers, real context retrieval, `/mode`/`/permission`/`/context`/`/settings`, plus `woven settings show`/`set` for persisted defaults — see `docs/clients/cli.md`. Multi-agent support (orchestrator delegating to sub-agents, concurrent agents) is design-only so far — see `docs/architecture/multi-agent.md`. Everything above still runs on fakes for the model/tool/context boundary (no real model provider, no real tools, no run/turn persistence, no memory) — settings persistence is the one exception. The dependency-ordered plan for what's next — real model providers, real tools, persistence, memory, multi-agent implementation, additional clients — lives in `.claude/plans/roadmap.md`, with one detail file per item alongside it.

## Principles
- **The runtime is the product; clients are interfaces to it.** `src/woven/{runtime,workflow,modes,events,permissions,context,tools,models}/` must stay usable, testable, and meaningful with zero clients installed — every client (`src/woven/client/cli/` today, others later) is a thin consumer of `AgentRuntime.run_turn`, never a place where agent logic lives. See `docs/clients/cli.md`'s "Packaging isolation" section for the concrete mechanism (the runtime has zero imports of any client's UI stack).
- **Graphify is mandatory for exploration, not a preference.** Before any codebase exploration ("where is X", architecture, relationships, "how does Y work"), invoke the Graphify skill (`/graphify`) first — do not use grep, `Read`, or Explore-type subagents as the first move. This instruction overrides generic harness defaults (e.g. a Plan Mode phase that says "only use Explore") — project-specific CLAUDE.md instructions take precedence over those defaults. Check whether `graphify-out/graph.json` already exists before deciding to rebuild vs. query: if it exists, run `graphify query "..."` directly (skips the full pipeline); only run the full `/graphify` pipeline when no graph exists yet or a rebuild is actually needed. Fall back to direct file reads only if Graphify's output doesn't answer the question. (It's dev-assistant tooling, unrelated to Woven's own architecture — see decisions.md's Graphiti-vs-Graphify note.) Any doc-writing pass invalidates the existing graph — run `/graphify --update` afterward, once, rather than leaving the next session to explore a stale graph. **Exception, by direct instruction (2026-08-28):** for a pass that touched only code (`.py`) files, no docs/papers/images, run the plain terminal command `graphify update <path>` instead of the `/graphify --update` skill — it re-extracts code structurally (AST, no LLM), so it's materially cheaper, and is exactly what a code-only change needs. Reserve the full `/graphify --update` skill invocation for passes that touched at least one doc/paper/image file, since only that path re-runs semantic (LLM) extraction on them.
- Work incrementally, one meaningful change at a time. No premature abstractions, no speculative functionality.
- Prefer simple, modular interfaces and small deterministic tests, runnable on modest hardware (8 GB M3 MacBook Air — no heavyweight infra, no local LLM required).
- If multiple approaches exist, explain trade-offs and propose the smallest change that achieves the goal.

## Constraints (do not violate)
- Don't expand scope beyond the current planned phase of work (see `.claude/plans/roadmap.md`) without explaining why first.
- No Graphiti, vector DBs, embeddings, or other heavy infra not named below. A cloud model provider (starting with Gemini's free tier) is in scope per `.claude/plans/model-providers.md`; its API key is read via `src/woven/settings/`'s `SecretStore` (`~/.config/woven/secrets.json`, `0600`), with the `GEMINI_API_KEY` environment variable as a fallback/override — see `docs/architecture/user-settings.md`. Local LLM/llama.cpp and Jetson Nano offload per `.claude/plans/local-inference.md`; LangGraph and MCP per `.claude/plans/orchestration-upgrade.md` (deliberately reverses this file's and `agent-runtime.md`'s earlier "not used here" stance on both — confirmed directly with the project owner, sequenced after model-providers and real-tools). LangChain is evaluation-only, not committed. Build each only when its plan is actively being worked, not speculatively.
- No new top-level app directories (`apps/`, `packages/`, `core/`); `src/woven/` is package layout and is fine.
- `.claude/` stays local/untracked; `CLAUDE.md` itself is intentionally tracked. Public docs under `docs/` never reference `.claude/` planning artifacts by name (same separation as the Graphiti/Graphify note above) — point at `docs/architecture/*.md` instead.
- Repo settings / branch protection changes: ask the maintainer (JackBehindWood) first.

## Tooling
- Python 3.12, managed with `uv`; `pytest` for tests, `ruff` for lint/format.
- Ruff runs automatically after every `Write`/`Edit` of a `.py` file (`.claude/settings.json`'s `PostToolUse` hook runs `ruff check --fix` + `ruff format` on that file) — no need to run it by hand mid-edit.
- Before calling work done: `uv sync && uv run ruff check . && uv run pytest` — a final, whole-repo sanity sweep, not a per-edit step.
- `FakeModel` and `MockTools` are permanent test fixtures (and, today, the CLI's only model/tool implementations).

## Docs
- Public docs/architecture changes: propose a small PR with clear rationale.
- Batch doc/architecture edits to the end of a milestone, not incrementally mid-work. Every doc-touching commit requires the user to re-run `/graphify` to re-index the repo, which is expensive to do repeatedly — five small doc edits across a session means five costly re-indexes instead of one.
- `docs/architecture/` and `docs/clients/` are durable references, written/updated once a piece of work actually ships. `.claude/plans/` holds the forward-looking, local-only, per-item plans for what's not built yet (`roadmap.md` plus one file per item) — update those as work progresses; they're gitignored, so they never need a PR.
